A scroll-driven Three.js camera that simply lerps toward its target — camera.position.y += (target.y - camera.position.y) * 0.05 — has a characteristic problem: it slows exponentially as it approaches the destination. The last ten percent of the travel takes as long as the first fifty. At low scroll velocities, the camera feels stuck. At high velocities it feels floaty, because it overshoots gracefully but decelerates without any weight.

Deep Signal's camera uses a damped spring instead. The spring produces a natural arrival with a single visible overshoot and then settles — the same physical feel as a camera weighted on a good dolly track. This post explains the implementation, the constants chosen, and why frame-rate independence requires more care with a spring than with a lerp.

The lerp problem

The standard smooth-follow pattern — multiply the gap by a small coefficient each frame — is sometimes called "lerp easing" but it is actually exponential decay. Each frame closes a fixed percentage of the remaining gap. When 95% of the gap has closed, closing another 5% moves the camera barely at all.

This creates two problems:

  • The camera never arrives. Mathematically, exponential decay asymptotically approaches zero but never reaches it. In practice, floating point rounds to zero eventually, but the visual effect is a camera that decelerates to an imperceptible crawl for the last few frames rather than arriving cleanly.
  • Coefficient changes with frame rate. A coefficient of 0.055 at 60fps gives a very different feel at 8fps (SwiftShader) or 120fps. The effective settling time is tied to the number of frames, not wall-clock seconds.
A lerp coefficient is not a physical constant. It is a per-frame multiplier that produces completely different behaviour across frame rates without obvious debugging symptoms.

The correct frame-rate-independent lerp uses 1 - pow(1 - alpha, dt * 60) as the coefficient, scaling alpha by the elapsed time. But once you are doing that, a damped spring is not much more complex and produces a far more natural result.

The damped spring equations

A damped spring tracks position and velocity. Each frame, the spring force accelerates the velocity toward the target, and damping reduces velocity over time:

// Spring state — persists between frames
const spring = { pos: 0, vel: 0 };

function stepSpring(spring, target, dt) {
  const STIFFNESS = 12;    // spring constant — higher = snappier
  const DAMPING = 0.0015;  // per-second velocity multiplier (< 1 = decay)

  // Spring force: proportional to displacement
  const force = (target - spring.pos) * STIFFNESS;
  spring.vel += force * dt;

  // Damping: exponential decay, frame-rate independent
  spring.vel *= Math.pow(DAMPING, dt);

  spring.pos += spring.vel * dt;
  return spring.pos;
}

The critical line is Math.pow(DAMPING, dt). This is the frame-rate-independent form of velocity damping. The simpler form spring.vel *= (1 - DAMPING * dt) produces different damping ratios at different frame rates — at 8fps it damps far more aggressively per frame than at 60fps. The exponential form computes the correct multiplier for the actual elapsed time regardless of the frame rate.

At each frame, the camera Y position is set directly from spring.pos. There is no lerp between frames — the spring integration is the motion model.

Choosing the constants

The stiffness and damping constants interact. Stiffness controls how quickly the spring responds to a displacement — high stiffness snaps fast, low stiffness oscillates slowly. Damping controls how quickly oscillations decay — low damping produces many overshoots (underdamped), high damping produces a slow crawl without overshoot (overdamped).

The constants used in Deep Signal were found by feel rather than formula:

  • Stiffness 12 — fast enough to keep the camera responsive to scroll without lag, slow enough to produce visible overshoot at chapter transitions.
  • Damping 0.0015 — produces exactly one visible overshoot before settling. Higher values would settle immediately (feels rigid); lower values would oscillate for several seconds (feels bouncy).
  • dt clamped to 100ms — prevents a tab returning from background from launching the camera across the scene in one frame.

A useful calibration technique: set stiffness high (30+) and damping near 1.0 to observe a rigid snap, then reduce damping until you see the first overshoot, then reduce stiffness until the arrival speed feels natural. Work from the extremes inward rather than guessing at the middle.

Chapter stops and scroll input

Deep Signal's camera visits five distinct positions — SURFACE, DESCENT, THE VEIN, THE CORE, RESURFACE. The camera does not smoothly interpolate between chapters; it commits to one chapter stop at a time, and the spring produces the glide between stops.

The scroll progress (0–1 over the full page height) maps to a chapter index using fixed thresholds. The chapter is only committed once progress passes the threshold by a margin — the 42% offset mentioned in the fallback architecture post:

// Chapter thresholds (0-1 scroll progress)
const THRESHOLDS = [0, 0.18, 0.38, 0.62, 0.80];
const CHAPTER_POSITIONS = [0, -14, -32, -51, -8]; // world Y

function getTargetY(scrollProgress) {
  // Find the current chapter: threshold must be passed by 0.04 before committing
  let chapter = 0;
  for (let i = 1; i < THRESHOLDS.length; i++) {
    if (scrollProgress > THRESHOLDS[i] + 0.04) chapter = i;
  }
  return CHAPTER_POSITIONS[chapter];
}

The 0.04 hysteresis prevents the camera from toggling between two chapters when scroll velocity puts progress exactly on a threshold. Without it, a slow scroll near the chapter boundary produces rapid chapter transitions that spike the spring.

The spring target is updated every frame from getTargetY. The spring smoothly chases the target — so when the chapter commits and the target jumps from position A to position B, the spring glides rather than teleports.

Frame-rate independence

The spring integration requires accurate delta time. Three.js's Clock.getDelta() provides this in seconds. The implementation clamps delta time to a maximum of 100ms to prevent large jumps when the tab was backgrounded:

function onFrame() {
  const rawDt = clock.getDelta();
  const dt = Math.min(rawDt, 0.1); // clamp to 100ms max

  const targetY = getTargetY(scrollProgress);
  camera.position.y = stepSpring(spring, targetY, dt);

  renderer.render(scene, camera);
  requestAnimationFrame(onFrame);
}

Without the clamp, a tab that is backgrounded for 30 seconds and then brought back has a pending dt of 30 seconds. The spring integration runs at 30 × STIFFNESS × displacement force, which launches the camera hundreds of units in one frame. The clamp limits this to 100ms of accumulated movement regardless of how long the tab was inactive.

The adaptive quality governor interacts with the spring at LOW tier: the reduced frame rate on slow hardware means each spring step is larger, which can make the camera feel more responsive (fewer, larger steps) rather than smoother. This is acceptable at LOW tier — at that performance level, physical accuracy is less important than keeping the page interactive.

The QA gotcha

The spring creates a specific QA problem: tests that assert on camera position must wait for the spring to settle. With SwiftShader at 8fps, a spring with stiffness 12 and damping 0.0015 takes about 8–10 real seconds to settle to within 1% of its target from a full-chapter-distance away.

The smoke suite avoids asserting on camera position directly. Instead, it uses the chapter index from __labQ().qIdx (which only advances when the camera is within range of the target position) and sleeps for 9 seconds after a large scroll jump before reading state:

// Scroll to chapter 3 (THE CORE)
await evalJs("window.scrollTo(0, document.body.scrollHeight * 0.65)");
// Wait for spring to settle on slow hardware
await sleep(9000);
// Now assert on chapter index
const { qIdx } = await evalJs("window.__labQ()");
assert(qIdx === 3, `expected chapter 3, got ${qIdx}`);

Tests that skip this sleep pass reliably on a fast local machine with a real GPU and fail intermittently on CI. The 9-second value was measured from actual frame timing on the Actions runner — not guessed.
