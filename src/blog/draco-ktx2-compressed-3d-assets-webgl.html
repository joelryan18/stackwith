Deep Signal's crystal shaft uses a custom Blender-authored geometry bundle — 1,600 instanced shards plus a bevelled gem hero — compressed down to 36 KB of geometry and two matcap textures totalling about 680 KB. Without compression, the raw geometry would be around 370 KB and the textures would be 12 MB. This note explains the pipeline that achieves those ratios and the specific settings that matter.

Pipeline overview

The pipeline runs outside the normal npm build — Blender and toktx are machine-level dependencies, not npm packages, so the generated files are committed to the repository rather than regenerated on the CI runner. This means the pipeline is run once when geometry changes and the resulting assets are versioned alongside the code.

The steps are:

  1. A Python script (gen_crystals.py) runs headlessly in Blender to create geometry, apply modifiers, bake a Cycles matcap render, and export a glTF with mesh data.
  2. build-3d.mjs applies Draco compression to the exported glTF via gltf-pipeline.
  3. toktx (from the KTX-Software package) encodes the PNG matcap renders to KTX2 UASTC format with optional Rate Distortion Optimization.
  4. The resulting .glb and .ktx2 files land in src/assets/3d/ and are served as static assets.

Headless Blender export

Running Blender headlessly means passing a Python script via blender --background --python gen_crystals.py. The script constructs geometry entirely through the bmesh API — no human-visible Blender interface is needed. This makes the geometry deterministic and reproducible: the same script run on any machine produces the same asset.

The matcap bake happens inside the same script. A studio lighting rig (warm key, cyan rim, lime kick, magenta fill) is set up in Blender's scene, and a Cycles bake renders the result onto a UV sphere. The sphere's UV space maps directly to the view-normal space that the runtime shader samples when rendering with a matcap — top of the UV corresponds to the top of the normal hemisphere, which is the lit direction in eye space.

The bake resolution matters more than the sample count. At 512², the matcap looks visibly soft. At 1024², it has enough detail for the spectral glints that make the crystal look sharp. Going to 2048² adds little visual quality but doubles the texture cost.

Draco geometry compression

Draco is a Google-developed codec for 3D geometry that represents mesh positions as quantised integers on a prediction-coded connectivity graph. The practical ratio for this use case — crystalline prisms with clean topology and no UVs — is about 10:1 compared to raw binary glTF.

The key settings are quantisation bits for position, normal, and colour attributes. Higher quantisation means smaller files but visible stepping artefacts in the geometry. The settings used here:

  • Position: 14 bits — sufficient for ~50-unit scenes without visible stepping.
  • Normal: 10 bits — normals have angular quantisation artefacts at low bit depths; 10 is the practical floor for smooth lighting.
  • Colour: 8 bits — vertex colours (the tint channel on the crystal variants) do not need more than 8 bits.

Draco decompression happens in the browser via DRACOLoader from the three.js extras. The decoder WASM and JS are served from /assets/3d/draco/ as static files — they must be on the same origin as the page for the worker to load them. The loader is configured to use the worker (not the inline fallback) for better performance:

const draco = new DRACOLoader();
draco.setDecoderPath("/assets/3d/draco/");
draco.setDecoderConfig({ type: "wasm" }); // prefer WASM over JS fallback

KTX2 UASTC texture encoding

KTX2 is a container format for GPU-compressed textures. The UASTC codec within it produces textures that can be transcoded to ASTC (mobile), BC7 (desktop), or ETC2 (fallback) at load time, depending on what the GPU supports. This means one KTX2 file serves all GPU families without shipping format-specific variants.

The toktx command for a 1024² matcap looks like:

toktx --t2 --encode uastc --uastc_quality 3 \
      --genmipmap --assign_oetf linear \
      output.ktx2 input.png

The --assign_oetf linear flag is important for matcap textures, which are not sRGB images — they are already in linear light. Marking them as sRGB would cause the renderer to apply gamma correction a second time, washing out the dark values. The three.js KTX2Loader respects this metadata and sets texture.colorSpace accordingly.

For the interior refraction matcap, Rate Distortion Optimization (--uastc_rdo_l 1.5) is added. RDO trades a small amount of quality for better entropy compression, reducing the DEFLATE'd file size by another 10–20% after the UASTC encoding. The quality loss is not perceptible on a texture that is already sampled through a refract() distortion.

Runtime loading

At runtime, three.js GLTFLoader with the DRACOLoader extension handles the glb, and KTX2Loader handles the matcap textures. Both are initialised once and reused across load calls — creating a new loader per asset wastes the WASM initialisation cost.

The KTX2Loader requires a reference to the renderer to detect GPU texture format support:

const ktx2 = new KTX2Loader();
ktx2.setTranscoderPath("/assets/3d/basis/");
ktx2.detectSupport(renderer); // must be called before any load

The asset names in the GLB are used as a stable identifier for runtime placement. This means geometry names set in Blender (like Shard0, Gate, Cradle) become the API surface between the export pipeline and the runtime. If a name changes in Blender and the export runs without updating the runtime lookup, the node is silently missing rather than causing an error — the runtime guards all name lookups with a null check and falls back to the no-3D presentation if a required node is absent.

Axis and colour gotchas

The most expensive mistake in this pipeline is the axis orientation trap. Blender uses a Z-up coordinate system internally, but glTF is Y-up by default. The Blender glTF exporter's export_yup=True default converts Z-up geometry to Y-up on export — which is correct for geometry designed in Blender's coordinate system. But if the geometry is authored in Y-up coordinates inside Blender (because the runtime wants Y-up without conversion), exporting with export_yup=True rotates it 90° and it arrives on its side.

The fix is to set export_yup=False when exporting geometry authored in Blender's Y-up. This sounds backwards but is correct: you are telling the exporter not to apply the axis conversion that it would otherwise apply.

The second gotcha is vertex colour defaults. A mesh with no COLOR_0 attribute gets three.js's default white colour in a ShaderMaterial attribute — attribute vec4 color reads (1,1,1,1) instead of zero. For the crystal tint channel, this meant every crystal rendered at full tint before the per-instance aTint attribute was applied, washing the dark navy body white. The fix is to bake an explicit zero vertex colour on any mesh that uses the tint attribute but should start uncoloured.
