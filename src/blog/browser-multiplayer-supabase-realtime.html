Signal Strike supports up to four human players in the same match, with bots filling the remaining roster to a full twelve. The multiplayer layer uses Supabase Realtime — specifically its broadcast and presence channels — with no dedicated game server. One browser tab is the authoritative host; the others are peers. This note explains how that architecture works, what makes it viable for a browser game, and where it falls short.

Transport choice

Supabase Realtime provides two primitives over a single WebSocket connection: broadcast (fire-and-forget messages to all other subscribers on a named channel) and presence (a CRDT-based state sync where each client tracks a small state object and sees when others join or leave).

This is enough for a game with these properties: up to four humans, no persistent server-side game state, and favor-the-shooter hit detection. A traditional authoritative game server would add sub-20ms latency and deterministic anti-cheat guarantees that a browser demo does not need to meet.

The same game logic runs through two other transport adapters for testing: BroadcastChannel (same-browser, two-tab), and a scripted stub that simulates a second peer without any network. All three adapters implement the same send(type, data) and onMessage(handler) interface, so the game logic never directly references Supabase.

Host authority

The host is determined by the earliest join time. Each client tracks a joinT timestamp when it enters the Supabase presence channel. When the presence state changes — someone joins or leaves — every client computes Math.min(...peers.map(p => p.joinT)) and the client with the minimum join time is the host.

The host runs three things the peers do not:

  • Bot AI and bot positions — broadcast to peers at 8 Hz via bs (bot state) messages.
  • Storm / zone contraction — broadcast at 2 Hz via st messages.
  • Score authority — in Team Deathmatch, the host accumulates kills from all kill messages and broadcasts the authoritative score at 2 Hz plus on every kill event.

When the host leaves, every remaining client recomputes the host independently (they all have the same presence data) and the new host starts running bots and storm from the next tick. This is called silent promotion — no coordination message is needed because the election algorithm is deterministic and shared.

const recomputeHost = () => {
  const all = [...NET.peers.values(), NET.self];
  all.sort((a, b) => a.joinT - b.joinT);
  const wasHost = NET.amHost;
  NET.amHost = all[0].id === NET.self.id;
  if (NET.amHost && !wasHost) assumeHostAuthority();
};

Wire messages

The wire protocol is a set of typed message objects sent via broadcast. Each has a type field and a payload. The key messages are:

  • snap — position snapshot for a player: {id, x, y, z, rx, ry, rz, vel, pt} at 10 Hz.
  • shot — a fired shot: {id, tx, ty, tz, d, w, bid}. d is a boolean flag for high-damage weapons; w is the weapon index; bid identifies the shooter.
  • hit — a successful hit: {bid, tid, dmg, hp}. The shooter broadcasts this; the target adopts the HP value.
  • died — death notification: {bid, kt} where kt is the killer's team ID.
  • bs — host-broadcast bot state array.
  • sc — score update from host: {a, b, mt, fin}.

The design is favor-the-shooter: the shooter's client determines whether a shot landed and broadcasts the hit. Peers accept hit messages from any client without re-validating the geometry. This gives snappy local feedback at the cost of being exploitable in a competitive context — which is acceptable for a browser demo but not for a ranked game.

Snapshot interpolation

Each client broadcasts its position at 10 Hz. Peers receive these at irregular intervals depending on network conditions. Rendering the received position directly produces jitter. Interpolation fixes this by maintaining a small buffer of the last two snapshots and rendering the interpolated position at a fixed lag behind the leading edge.

The interpolation fraction is calculated as:

// dt = frame delta time; lag = 100ms interpolation window
peerState.interpT += dt;
const t = Math.min(peerState.interpT / lag, 1.0);
peerRig.position.lerpVectors(peerState.prevSnap.pos, peerState.currSnap.pos, t);

When a new snapshot arrives, prevSnap becomes currSnap and the new data becomes currSnap, and interpT resets to zero. This produces smooth interpolated movement even with 200 ms packet spacing.

Velocity Y is also interpolated via the same mechanism, so airborne peers look correctly affected by gravity rather than teleporting vertically.

Validation and security

Without a server, the wire is effectively public — any client can send any message to the channel. The validation layer defends against accidental errors (a client sending a NaN position) and prevents obviously broken state from corrupting the simulation:

  • All numeric fields in snap messages are gated by Number.isFinite(). A NaN or Infinity in a position snaps the peer to (0,0,0) rather than breaking the scene graph.
  • Damage values in hit messages are clamped to saneDmg = 220 — the maximum possible from a shotgun hitting all pellets at full damage. Any message claiming more than that is clamped before application.
  • Player names from presence data are run through a feedName(s) sanitiser before being inserted as innerHTML in the kill feed.
  • The peers map is capped at 16 entries. A client that creates many presence entries cannot allocate unbounded memory.

Testing two tabs

The most reliable way to integration-test a multiplayer game is to run two real browser tabs with a shared room code. Doing this headlessly via CDP requires several non-obvious setup steps:

  • Each tab must be created in its own browser context (Target.createBrowserContext) so they do not share localStorage or IndexedDB. Two tabs in the same context would have the same Supabase session token and appear as the same user.
  • All three of --disable-background-timer-throttling, --disable-renderer-backgrounding, and --disable-backgrounding-occluded-windows must be passed to Chrome. Without these, the unfocused tab's requestAnimationFrame loop stops, the glider never lands, and position snapshots freeze mid-air.
  • Tracking fire (re-aiming at the target every 90ms while holding the trigger) is more reliable than a single aimed shot for hit registration tests, because a bot orbiting at 10 m/s moves about 0.9 m per frame at 10 fps, which exceeds the hitscan tolerance of a single aim.

The two-tab QA driver (/tmp/game-squad-v4-qa.mjs) covers: room creation and auto-join via the invite link, presence sync showing two players, host election, match start, snapshot flow, score sync from host to guest, guest respawn visible to host, and room shrink on tab close.

Limits of this architecture

This architecture is designed for a browser demo, not a competitive title. The specific limits are:

  • No cheat prevention. The shooter determines hits. Any client can broadcast false hit messages.
  • Host advantage. The host runs at zero latency for bot decisions. A peer fighting a bot is receiving positions that are 50–200ms stale.
  • No reconnection. If a client loses its WebSocket connection, it cannot rejoin the same match. There is no state snapshot to resume from.
  • Supabase message limits. Free-tier Supabase Realtime has rate limits. A 12-player match broadcasting at 10 Hz generates around 1,440 messages per minute, which can hit those limits under stress.

These are documented trade-offs, not accidental gaps. The nice-to-have list for a production implementation would include server-side validation, reconnection tokens, and a proper lag compensation model. A browser demo for a portfolio site does not need any of those things to be valuable or honest about what it is.
