AXON began as an interface question: if software were allowed to choose and act, what would a responsible operator need to see before trusting it? The answer was not another chat transcript. It was a structured audit trail that made the decision legible.

The page at AXON's simulated trace is a design study, not output from a deployed agent platform. Its value is in the information architecture: it shows which facts should be captured and where a human should be able to interrupt the process.

The interface problem

Traditional automation usually exposes a small state machine: queued, running, succeeded, or failed. An agent-like system introduces another question: why did it select this action instead of another? Recording only the outcome erases the part an operator needs to review.

That led to a simple design rule for AXON: the trace is not a debug drawer. It is the product surface. The simulated console is placed alongside the feature explanation, and the visual language repeatedly routes the reader through sense, plan, act, and observe.

If a system is presented as making choices, its interface should make those choices inspectable.

The four-part trace shape

The showcase models four groups of information:

  • Sense — the event, inputs, source, and time the system observed.
  • Plan — candidate paths, expected outcomes, confidence, and rejected options.
  • Act — proposed or completed tool calls, arguments, results, and side effects.
  • Observe — verification, changed state, cost, escalation, and remaining uncertainty.

The distinction between “proposed” and “completed” matters. A trustworthy trace should never make a planned action look executed. The AXON page now labels its console as simulated because the interface demonstrates the shape without a live agent behind it.

Decision boundaries and approval gates

A useful trace also shows where autonomy stops. Refunds, destructive database changes, and permission changes are examples of actions that may require human approval. The gate should receive the same context as the agent: input evidence, chosen path, alternatives, and expected impact.

This is why the design pairs an immutable-looking ledger with scoped permissions. The idea is architectural, not a claim that stackwith.me operates such a production system. The companion note Guardrails are a feature examines that boundary in more detail.

What is implemented here

  • A real Eleventy page and responsive interface.
  • A browser-rendered, animated example trace.
  • Sections that explain the proposed sense-plan-act-observe loop.
  • Cross-links between the interface study and these design notes.
  • Explicit labels separating the live interface from the simulated service.

The implementation can demonstrate whether the concepts are understandable, whether the trace hierarchy is readable, and whether the disclosure remains visible. It cannot validate model quality, policy enforcement, or production reliability.

What the showcase cannot prove

  • There is no deployed AXON orchestration service behind the animated console.
  • The example does not establish latency, uptime, connector coverage, or workload volume.
  • A real audit system would need tamper resistance, retention policy, access controls, redaction, and export semantics.
  • Exposing hidden model reasoning is not the same as providing a reliable decision record; a production design should log evidence, decisions, tool activity, and verification without promising access to private chain-of-thought.

The useful outcome is narrower and more honest: the showcase provides a concrete interface vocabulary for discussing inspectability before anyone builds the backend.
