The original AXON concept used “sub-40ms orchestration” as a product line. Without a deployed orchestrator and repeatable benchmark, that wording looked like a measured result. It was not. This note keeps the useful part—the latency budget—and removes the unsupported claim.

A latency target can still shape architecture. It forces each synchronous hop to justify its place and makes hidden queueing visible. The honest label is design target until a real implementation, workload, environment, and distribution of results exist.

Start with a budget

A hand-off budget is the time between one component deciding that another component should act and the receiver accepting enough context to begin. It should not quietly exclude routing, authorization, serialization, or trace acknowledgement if those operations block the action.

For a hypothetical 40ms target, an initial budget might reserve time for:

  • input validation and authorization;
  • routing and receiver selection;
  • context serialization and transport;
  • receiver acknowledgement;
  • a small tail-latency reserve.

The allocation is not a benchmark. It is a checklist that prevents the headline number from floating free of an architecture.

Define the hot path

The AXON design proposes keeping likely collaborators close to one another and avoiding a central scheduler round trip for every decision. That proposal has trade-offs: placement becomes harder, state can diverge, and failover requires explicit ownership.

Authorization also belongs in the budget. Precomputed policy decisions may reduce network hops, but they introduce policy-distribution and revocation questions. A fast stale policy is not a successful guardrail.

Move non-decisions away

Metrics aggregation, long-term memory indexing, analytics, and rich trace storage do not necessarily need to block the receiver. They can be processed asynchronously if the system has durable delivery, backpressure, and reconciliation.

The important distinction is between “off the hot path” and “best effort.” An audit event can be asynchronous while still being required. The system needs a failure mode when the event cannot be durably accepted.

What a real benchmark requires

  • A named implementation and version.
  • Regions, hardware, runtime, transport, and payload size.
  • Warm and cold paths reported separately.
  • A realistic concurrency model and failure injection.
  • Percentiles, sample count, time window, and raw or reproducible data.
  • A precise start and stop definition.

Until those details exist, stackwith.me does not claim production p99 figures, workload volume, or customer results.

What the current page implements

The signal path is an animated explanation of connect, reason, act, and observe. The console is simulated, and the page labels the orchestration value as a target. The interaction can test whether the architecture is understandable; it cannot test whether the architecture meets the target.

That correction is part of the design work. A performance number should become more specific as evidence improves, not more confident as marketing copy improves.
