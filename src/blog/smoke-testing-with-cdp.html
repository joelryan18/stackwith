Every push to stackwith.me runs a browser-level smoke suite before anything goes live. Not a linter, not a unit test — a real headless Chrome instance visiting every page, evaluating JavaScript hooks, and asserting on the actual rendered state. The harness uses the Chrome DevTools Protocol directly, with no additional test framework sitting between the runner and the browser.

This note explains why that choice was made, how the sessions are structured, and the specific gotchas that are not obvious from the CDP documentation.

Why raw CDP

The reason for bypassing a higher-level framework is control. Playwright and Puppeteer are excellent tools, but they add opinions about timing, retry logic, and page lifecycle management that can mask the actual failure you are trying to detect. When a WebGL page takes 12 seconds to boot on SwiftShader and the test framework has a default 5-second element-wait, the framework hides the latency rather than surfacing it.

Raw CDP also makes it straightforward to use the exact Chrome binary installed on the machine — including flags like --disable-background-timer-throttling and --disable-renderer-backgrounding that are essential when opening multiple tabs and caring about rAF cadence in each.

The test harness should report what the browser actually did, not what the framework abstracted away.

Session setup

A CDP session starts by spawning Chrome with --remote-debugging-port=9222 and then connecting over WebSocket to the /json/version endpoint. The runner then opens target pages via Target.createTarget and attaches to them with Target.attachToTarget.

// Spawn Chrome with the right flags
const chrome = spawn(CHROME_BIN, [
  "--headless=new",
  "--remote-debugging-port=9222",
  "--disable-background-timer-throttling",
  "--disable-renderer-backgrounding",
  "--disable-backgrounding-occluded-windows",
  "--autoplay-policy=no-user-gesture-required",
]);

The --autoplay-policy=no-user-gesture-required flag matters for pages that create an AudioContext on boot — without it, the Web Audio graph initialises but the context remains suspended and any tests that assert on audio state silently fail.

For two-tab tests (like the Supabase multiplayer integration), each tab must be created in a new browser context with Target.createBrowserContext first, otherwise the tabs share the same localStorage and the second tab's auth session overwrites the first's.

QA hooks in the page

The pages expose lightweight JavaScript objects under names like __gameQ(), __labQ(), and __hubQ(). These are functions — not properties — so calling them always returns a fresh snapshot of the current runtime state rather than a value that was correct at some earlier point.

The convention is: __pageQ() returns a plain object with every state variable the smoke suite might want to check. It is defined only in production builds; the ?sim=1 URL parameter is required for the driver API.

Evaluating a hook from the runner looks like this:

const result = await cdp.send("Runtime.evaluate", {
  expression: "__gameQ()",
  returnByValue: true,
  awaitPromise: false,
});
const state = result.result.value;

An important restriction: the expression must be a pure expression, not a statement. Wrapping it in { return __gameQ(); } causes the Runtime to swallow the return value. If you need multiple statements, use an IIFE: (function(){ return __gameQ(); })().

Testing WebGL boot markers

WebGL pages go through an asynchronous boot sequence: parse HTML, execute JavaScript, request animation frames, load assets over the network, and finally render the first real frame. A naive check for element visibility fails because the element can be present in the DOM while the world is still initialising.

The solution is body-class markers. Each page adds a CSS class to document.body only when the world has actually booted — lab-crystalline appears on lab.html only after the GLB and KTX2 assets have loaded and the first instanced-mesh frame has been committed, for example. The smoke suite polls for these markers with a timeout:

const waitForClass = async (cdp, cls, timeoutMs = 15000) => {
  const start = Date.now();
  while (Date.now() - start < timeoutMs) {
    const { result } = await cdp.send("Runtime.evaluate", {
      expression: `document.body.classList.contains("${cls}")`,
      returnByValue: true,
    });
    if (result.value === true) return true;
    await sleep(300);
  }
  throw new Error(`Timed out waiting for body class "${cls}"`);
};

The same pattern works for checking that an experience did not boot when it should not have — asserting that game-no3d is present on a mobile-emulated viewport, for example.

Gotchas that cost hours

These are the non-obvious failures that required investigation rather than a quick fix:

  • Lexical scope across separate evaluate calls. Two separate Runtime.evaluate calls that each declare const foo = ... at the top level share the page's lexical scope. The second call throws a redeclaration error. Wrap every multi-statement evaluate block in { } to create a new scope, or use let.
  • Background tab throttling. Chrome throttles rAF and setInterval in tabs that are not the active foreground tab. A two-tab test where one tab's game loop never advances is almost always this — the fix is the three --disable-*backgrounding* Chrome flags listed above, combined with Emulation.setFocusEmulationEnabled.
  • GitHub Actions JSON with control characters. The GitHub API sometimes returns JSON with literal control characters (0x08, 0x0A mid-string) in commit message fields. JSON.parse throws. The fix is json.JSONDecoder(strict=False) on the Python side, or a pre-filter that strips control characters before parsing.
  • SwiftShader timing. On GitHub Actions runners, Chrome uses SwiftShader (the software GL renderer) at about 8 fps. Tests that rely on animations settling need sleep values of 8–10 seconds rather than 1–2. A camera lerp with coefficient 0.055 takes about 8 seconds to settle to within 1% of its target at that frame rate.
  • Supabase Realtime two-tab isolation. Opening two tabs in the same browser context means they share IndexedDB and localStorage. The second tab's Supabase client reads the first tab's session token and thinks it is the same user. Each tab must be in its own browser context, created with Target.createBrowserContext.

What the suite currently asserts

The suite runs across every page of this site on every push and covers:

  • HTTP 200 for every HTML page, CSS bundle, JS bundle, font, and 3D asset.
  • Absence of JavaScript exceptions on every page load.
  • WebGL boot markers on lab.html, game.html, and about.html.
  • Correct fallback classes on small-screen and reduced-motion emulation.
  • Checkout flow: plan detection, consent gate, sign-in stage.
  • Multiplayer: stub peer, BroadcastChannel two-tab, and Supabase two-tab room creation.
  • Content honesty strings: exact phrases pinned so copy changes require explicit smoke updates.

The total is over 300 checks as of this writing. When a check fails, the build stops and nothing goes to GitHub Pages. That threshold is the honest version of "tested before deploy."
